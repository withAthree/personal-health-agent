# 中间过程可见 —— 设计方案

> 目标：把"只看到模型最终回复"改为"看到思考、工具调用、压缩、用量等全部中间过程"，
> 对标 DeepSeek / LibreChat / OpenHands / WorkBuddy 一类产品的执行时间线体验。
>
> 状态：设计冻结（协议 v1），实现见 `document/中间过程可见-开发计划.md`。

---

## 一、背景与目标

### 1.1 现状问题

1. 用户只能看到 assistant 气泡里逐字出现的正文，看不到模型在想什么。
2. 模型若开启推理（reasoning），推理内容被**后端主动丢弃**，用户完全无感。
3. 上下文压缩（SummarizationMiddleware）在用户不知情时发生，只用一个"以上 N 条已压成摘要"分隔条提示。
4. 用户刷新页面即丢失生成中的一切，"请求很慢"没有任何可观测信息。

### 1.2 目标

| 编号 | 目标 | 本期是否覆盖 |
|------|------|-------------|
| G1 | 流式展示模型思考过程（thinking） | 是 |
| G2 | 流式展示正文（text） | 是（沿用） |
| G3 | 展示工具调用与结果（tool_call / tool_result） | 否，Phase 3 |
| G4 | 展示上下文压缩事件 | 部分（发 `compaction` 事件） |
| G5 | 展示 token / 上下文用量 | 否，Phase 5 |
| G6 | 刷新页面后回放本轮已生成的过程 | 是（回放，不续跑） |
| G7 | 断开连接后任务继续、可重连 | 否，Phase 4 |
| G8 | 协议可扩展，新增过程类型不破坏前端 | 是 |

### 1.3 非目标（本期明确不做）

- 不改 `messages` 表结构与语义。
- 不改 LangGraph checkpoint 与摘要中间件行为。
- reasoning 不落 `messages` 表、不回喂模型。
- 不引入新运行时依赖，不依赖 `langchain_protocol`（版本 0.0.19，`_compat_bridge.py` 为下划线私有模块）。
- 不做连接与生成解耦（Phase 4），本期"刷新 = 本轮终止"语义不变。

## 二、现状（代码证据）

### 2.1 当前 SSE 协议

后端发点：`agent-app/src/agent_app/api/v1/chat.py:66`

```python
def _sse(payload: dict[str, Any]) -> dict[str, str]:
    return {"data": json.dumps(payload, ensure_ascii=False)}
```

只写 `data:` 行，不使用 SSE 的 `event:` 命名能力。四类事件：

| 事件 | 发点 | 负载 |
|------|------|------|
| `session` | `chat.py:501` | `session_id` |
| `chunk` | `chat.py:529` | `content`, `agent_source` |
| `error` | `chat.py:556`, `chat.py:566` | `content` |
| `done` | `chat.py:569` | `session_id` |

前端收点：`web-app/src/lib/api.ts:9` 的类型联合 + `api.ts:46` 的严格白名单：

```ts
if (type !== 'session' && type !== 'chunk' && type !== 'error' && type !== 'done') return null
```

**未知事件类型被静默丢弃** —— 这是协议扩容的第一个障碍。

### 2.2 中间过程为什么丢了

`agent-app/src/agent_app/api/v1/chat.py:79-87`：

```python
def _chunk_text(chunk: AIMessageChunk) -> str:
    """只提取字符串正文，忽略 reasoning 等非正文分片。"""
```

底层原因：`langchain_openai/chat_models/base.py:554` 的模块级函数 `_convert_delta_to_message_chunk(_dict, default_class)` 只取 `content` / `function_call` / `tool_calls`，非标准字段被丢弃。模块 docstring（`base.py:5-10`）明写第三方 provider 的 `reasoning_content` / `reasoning_details` "are **not** extracted or preserved"。

### 2.3 仍然保留的过滤（不能删）

`agent-app/src/agent_app/api/v1/chat.py:523`：

```python
if metadata.get("langgraph_node") != _MODEL_NODE: continue
```

这条过滤**不是**在挡中间过程，而是在挡 `SummarizationMiddleware.before_model` 那次 LLM 调用的输出（否则摘要正文会漏进用户气泡）。**方案中必须保留。**

### 2.4 账本不变量（改动红线）

`messages` 表是"账本" = 前端渲染的唯一来源 + 全量原文；LangGraph checkpoint 是"模型记忆" = 可压缩、可重建。以下四处逻辑依赖"账本只存 user / assistant 两类正文行"：

| 位置 | 依赖方式 |
|------|---------|
| `chat.py:331` `_to_model_messages(rows, *, skip_message_id)` | 跳过 `role='system'` 与 `interrupted` |
| `chat.py:357` `_drop_trailing_questions` | 只摘掉末尾的 `HumanMessage` |
| `chat.py:421` `_sync_compaction_marker` | 用 `账本条数 - checkpoint 非摘要条数` 推 `compacted_message_count` |
| `chat.py:173` `_retry_turn` | 靠 `role` 找 `last_user`，删其后 `interrupted` 行 |

**结论：不能往 `messages` 表插新的 role 或新语义的行。** 过程数据必须另存。

|------|------|

## 四、设计原则

1. **冻结信封，放宽内容。** 信封（事件命名规则、`index` / `step` / `block_id` 语义、生命周期）一旦冻结不再变；新增过程类型只是新增 `kind` 或新增 `type` 值。前端遵守"未知即忽略"，因此扩容是非破坏性变更。
2. **两层分离。** 传输层事件名保持少量且稳定；细粒度类型放在负载里。
3. **过程日志与模型上下文分离。** 过程数据绝不进 `messages` 表；模型上下文（checkpoint）不受影响。
4. **本轮聚合态可回放。** 过程数据在服务端保留一份本轮聚合态，刷新后可回放。
5. **fail-soft。** 过程可见是增强能力，不是安全边界。Redis 不可用时必须静默降级、对话照常，绝不能像 `core/token_store.py` 那样 fail-closed。

## 五、协议设计 v1

### 5.1 传输

保持"`data:` 行内带 `type`"，不使用 SSE `event:` 命名行。
理由：`chat.py:66` 不动；前端手写解析器（`api.ts:95/103`）不动。真正决定成败的是"两层分离 + 忽略未知类型"，而非 `event:` 行。（调研中未核对到这 5 家是走 `event:` 行还是 data 内 `type`，故不作为依据。）

### 5.2 信封

所有事件共用一个 `type` 字段；所有 block 类事件共用三个定位字段：

| 字段 | 语义 |
|------|------|
| `block_id` | 字符串，块身份。**`block-delta` 只引用它**（比 `index` 稳，因为 `reset` 会让 `index` 复用） |
| `index` | 整数，本 completion 内**绝对**槽位，从 0 起，跨 step 不重置（对应 LibreChat "Absolute content index"） |
| `step` | 整数，轮次，从 0 起。本期恒为 `0`；Phase 3 多 Agent 上线后才有意义 |

### 5.3 事件清单

| `type` | 负载 | 状态 | 说明 |
|--------|------|------|------|
| `session` | `session_id` | 沿用 | 首事件 |
| `run-start` | `run_id` | 新增 | 本轮标识，Phase 4 重连用 |
| `block-start` | `index, step, block_id, kind, meta?` | 新增 | 开一个块 |
| `block-delta` | `block_id, delta` | 新增 | 增量文本 |
| `block-stop` | `block_id, status` | 新增 | `status ∈ complete \| interrupted \| error` |
| `reset` | `from_index` | 新增 | 重新生成：前端丢弃 `index >= from_index` 的块（对齐 Vercel `reset-step`） |
| `compaction` | `covered, summary?` | 新增 | 摘要发生，复用 `_sync_compaction_marker` 的计数 |
| `usage` | `input_tokens, output_tokens` | 新增 | Phase 5 填充 |
| `done` | `session_id` | 沿用 | 结束 |
| `error` | `content` | 沿用 | 错误 |

### 5.4 `kind` 枚举

- **v1 实现**：`thinking` | `text`
- **预留（协议已允许，仅待实现）**：`tool_call` | `tool_result` | `plan` | `image` | `error`

`block-start` 的 `meta` 字段按 kind 定义。`thinking` 的 `meta` 预留：

```jsonc
{ "signature": "string|null", "redacted": "boolean|null" }
```

依据：LobeChat 的 `reasoning_signature` / `flagged_reasoning_signature`；OpenHands 的 "never render encrypted_content"。

### 5.5 `reset` 语义

触发：`ChatRequest.retry == true`（`agent-app/src/agent_app/schemas/chat.py:16`，语义见 `chat.py:173 _retry_turn`）。
行为：后端在 `session` 之后、第一块内容之前发 `{"type":"reset","from_index":0}`；前端清空本轮气泡的 `blocks`，但保留气泡本身（`retryTurn` 已经在做）。
对齐：Vercel `reset-step`。

### 5.6 未知类型处理（协议的一部分）

前端必须**忽略**未知 `type`（记 `console.debug`），不得静默 `return null`。
这条是"信封稳定、内容可加"的唯一前提，也是 5 家产品能不断加事件而不破坏客户端的原因。

### 5.7 过渡策略

**不双发** `chunk` 与 `block-*`。单一客户端 + 同一仓库，可原子切换。前端保留 `chunk` 解析分支一版以便回滚，实际不渲染。

## 六、存储设计

### 6.1 三层

| 层 | 内容 | 生命周期 | 本期改动 |
|----|------|---------|---------|
| `messages` 表（账本） | 只存**正文** | 永久 | **不动** |
| LangGraph checkpoint（模型记忆） | 模型消息，含 `additional_kwargs.reasoning_content` | 永久，可压缩 | **不动** |
| `stream_state`（新增） | 本轮 block 聚合态 | Redis，TTL 30 min | 新增 |

### 6.2 Redis 结构

- Key：`chat:stream:{session_id}`（一个 session 同时只有一个 run，新 run 覆盖旧值）
- Value：

```jsonc
{
  "run_id": "9f1c...",
  "status": "running | done | error | interrupted",
  "started_at": 1760000000.0,
  "finished_at": null,
  "blocks": [
    {"block_id": "b0", "index": 0, "step": 0, "kind": "thinking",
     "text": "...", "status": "complete", "meta": {"signature": null, "redacted": false}},
    {"block_id": "b1", "index": 1, "step": 0, "kind": "text",
     "text": "...", "status": "running", "meta": null}
  ],
  "compaction": {"covered": 12},
  "usage": {"input_tokens": 0, "output_tokens": 0}
}
```

### 6.3 写入策略

**delta 在内存累积，每 200ms flush 一次；`block-start` / `block-stop` / `reset` / 结束立即 flush。**

理由：thinking 分片速率可达 30–60/s，逐片写 Redis 不划算。200ms 是"刷新最多丢失 200ms 文本"与 Redis 压力之间的平衡点。

### 6.4 故障策略（与 `token_store` 相反）

`agent-app/src/agent_app/core/token_store.py` 是 **fail-closed**（Redis 不可用抛 `TokenStoreUnavailableError` → 503），因为它在判定权限，必须保守。

`stream_state` 必须 **fail-soft**：Redis 异常时记 warning、跳过读写、对话与流式照常，前端只是拿不到可回放的过程。
该差异必须写进 `core/stream_state.py` 的模块 docstring，防止后人"统一风格"改成 fail-closed 而把对话打挂。

### 6.5 刷新与重连语义（本期边界）

`chat.py:543-556` 的 `CancelledError` / `GeneratorExit` 分支会**取消上游请求**。本期**不改**：

- 用户刷新 → 上游被取消 → `_persist_interrupted`（`chat.py:480`）落"已终止"正文 → `stream_state.status = "interrupted"`，所有 `running` 块置 `interrupted`
- 刷新后前端挂载时 `GET /chat/{session_id}/stream-state` → 回放到中断点 → 显示"本轮已中断" → 复用现有重试入口

即：**本期解决"看得见"，不解决"接得住"**。连接与生成的解耦是 Phase 4。

## 七、后端实现

### 7.1 reasoning 提取（关键实现）

三处已验证事实：

1. `langchain_openai/chat_models/base.py:554` `_convert_delta_to_message_chunk` 是**模块级函数**，无法 override。
2. `base.py:1609` `_convert_chunk_to_generation_chunk` 是**实例方法**，可以 override。
3. **`chunk.content_blocks` 对 chat completions 的 reasoning 无用**：
   `langchain_core/messages/block_translators/openai.py:1062 translate_content_chunk` 判断 `isinstance(message.content, str)` → chat completions 流走 `_convert_to_v1_from_chat_completions_chunk`（`openai.py:229`），该函数**只产出 `text` 和 `tool_call` / `tool_call_chunk`**，完全不读 `additional_kwargs`。
   只有 Responses API（`content` 是 list）才走 `_convert_from_v03_ai_message`（`openai.py:291`），其 `:338` 才读 `additional_kwargs["reasoning"]`。
   → **后端必须直接读 `chunk.additional_kwargs`。**

安全保证（结构性，不靠自觉）：`_convert_message_to_dict`（`base.py:472-550`）只转发白名单 key —— `name` / `tool_calls` / `function_call` / `音频 audio` / `__openai_role__`。任意 `additional_kwargs` **不会**进入请求体，因此放在 `additional_kwargs["reasoning_content"]` 里的推理内容**永不回喂上游**。

实现（`agent-app/src/agent_app/llm/client.py`）：

```python
class ChatOpenAIWithReasoning(ChatOpenAI):
    """保留 provider 非标准字段 reasoning_content（ChatOpenAI 默认丢弃）。"""

    def _convert_chunk_to_generation_chunk(self, chunk, default_chunk_class, base_generation_info):
        result = super()._convert_chunk_to_generation_chunk(
            chunk, default_chunk_class, base_generation_info
        )
        if result is None:
            return None
        choices = chunk.get("choices") or chunk.get("chunk", {}).get("choices") or []
        if choices:
            delta = choices[0].get("delta") or {}
            if rc := delta.get("reasoning_content"):
                # 单分片直接赋值；跨分片累积由 LangChain merge_dicts 的 str 拼接语义负责
                result.message.additional_kwargs["reasoning_content"] = rc
        return result
```

- `chunk.text` → `("text", ...)`

### 7.4 `_stream_chat` 状态机

在 `chat.py:495 _stream_chat` 内，通过 `chat.py:523` 的节点过滤**之后**：

1. 首次遇到某 `kind` → 分配 `block_id` / `index` → 发 `block-start` → Redis `put_block_start`
2. 每次 delta → 发 `block-delta` → 内存累积（200ms flush）
3. `kind` 切换（thinking → text）→ 前一块 `block-stop{status:"complete"}`，新块 `block-start`
4. 流结束 → 未关闭块 `block-stop`，`put_finish(status)`
5. `CancelledError` / `GeneratorExit` → 未关闭块 `block-stop{status:"interrupted"}`，`put_finish("interrupted")`

### 7.5 新增接口

```
GET /api/v1/chat/{session_id}/stream-state
```

- 鉴权复用 `chat.py:591 _require_session`
- 返回 `StreamStateOut | null`（无记录返回 `null`）
- **不新增任何写入接口**（过程数据不落库）

### 7.6 新增 schema

`agent-app/src/agent_app/schemas/chat.py` 增加 `StreamBlockOut` / `StreamStateOut` / `StreamStatus`。
理由：`_sse(payload: dict)` 目前完全无约束，借这次把协议变成单一事实来源。
