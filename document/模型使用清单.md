# 模型使用清单

> 用途：把「这个项目在哪些地方用了大模型、用的是哪个模型、参数是什么」集中记在一处，
> 以便后续做**模型选型**时有据可依地替换，而不是随手换一个便宜的试试。
>
> 每新增一个模型调用点都要在本文件登记；每个调用点的「验收标准」一栏是这份文档的核心，
> 它决定换模型之后要拿什么标准去判断新旧模型谁更好。
>
> 代码位置按当前版本记录，改动代码后请同步更新本文件。

---

## 一、怎么读这份清单

- **开发期改 `agent-app/src/agent_app/config.py` 的默认值就行**：后端跑
  `uvicorn --reload`，改完进程自动重启、`lru_cache` 的客户端跟着重建，不用碰容器。
- **上线或临时切换才走 `.env`**（`agent-app/.env`，由 `docker/docker-compose.yml`
  的 `env_file` 注入）：`Settings` 用 `SettingsConfigDict(env_file=BASE_DIR / ".env")`
  读取，优先级是「环境变量 > 代码默认值」，所以 `.env` 里配了就覆盖代码默认值。
  这种情况**必须重建容器**：`docker compose restart backend` 不会重读 `env_file`，
  要用 `docker compose -f docker/docker-compose.yml up -d backend`。
- 变量命名与 `config.py` 字段的对应关系是「字段名大写」：`llm_model` ← `LLM_MODEL`，
  `llm_summary_model` ← `LLM_SUMMARY_MODEL`，`llm_memory_model` ← `LLM_MEMORY_MODEL`，
  `llm_parse_model` ← `LLM_PARSE_MODEL`，`llm_ds_model` ← `LLM_DS_MODEL`。
- 客户端都是 `@lru_cache(maxsize=1)` 单例：**换模型必须重启进程**（重启容器即可），
  热改环境变量不会让已有进程换模型。
- 各调用点共用的客户端工厂都在 `agent-app/src/agent_app/llm/client.py`：

  | 工厂 | 定义位置 | 用途 |
  |------|---------|------|
  | `get_llm()` | `agent-app/src/agent_app/llm/client.py:105` | 对话生成（要流式、要思考块） |
  | `get_summary_llm()` | `agent-app/src/agent_app/llm/client.py:122` | 上下文摘要（压缩），非流式 |
  | `get_memory_llm()` | `agent-app/src/agent_app/llm/client.py:132` | 长期记忆抽取，非流式 + 结构化输出 |
  | `get_parse_llm()` | `agent-app/src/agent_app/llm/client.py:142` | 文档解析抽取，非流式 + 结构化输出（唯一一个温度 0.0 的调用点） |
  | `get_ds_llm()` | `agent-app/src/agent_app/llm/client.py:158` | 数据分析子 Agent（Plan + Code），非流式 + 结构化输出 |

  `get_llm()` 返回 `ChatOpenAIWithReasoning`（`agent-app/src/agent_app/llm/client.py:52`），
  它修正了 provider 两处非标准行为：把 `reasoning_content` 从 `additional_kwargs`
  里捡回来、补上流式 usage。
  其余几个共用私有构造 `_build_utility_llm()`（`agent-app/src/agent_app/llm/client.py:179`），
  但**模型名各自独立**：分别由 `settings.llm_summary_model`、`settings.llm_memory_model`、
  `settings.llm_parse_model`、`settings.llm_ds_model` 决定，**留空表示回落到
  `settings.llm_model`**。

## 二、总览

| # | 用途 | 调用点 | 客户端 | 调用形态 | 频率 | 当前模型 |
|---|------|--------|--------|---------|------|---------|
| 1 | 对话生成 | `agent-app/src/agent_app/llm/agent.py:70`（装配）<br>`agent-app/src/agent_app/api/v1/chat.py:674`（发起） | `get_llm()` | 流式 + 思考块 | 每轮对话 1 次 | `settings.llm_model` |
| 2 | 上下文摘要 | `agent-app/src/agent_app/llm/context.py:132` | `get_summary_llm()` | 非流式、单轮 | 触发式（会话变长时） | `settings.llm_summary_model` → 回落 #1 |
| 3 | 长期记忆抽取 | `agent-app/src/agent_app/memory/extract.py:158` | `get_memory_llm()` | 非流式 + 结构化输出 | 每轮对话后台 1 次 | `settings.llm_memory_model` → 回落 #1 |
| 4 | 数据分析（DS 子 Agent） | `agent-app/src/agent_app/ds/graph.py:94`（装配在 `agent-app/src/agent_app/ds/graph.py:306` 的 `run_analysis()`） | `get_ds_llm()` | 非流式 + 结构化输出 | 每轮分析 2 次起（Plan 1 次 + Code 1~4 次） | `settings.llm_ds_model` |
| 5 | 文档解析抽取 | `agent-app/src/agent_app/parsing/extract.py:25` | `get_parse_llm()` | 非流式 + 结构化输出 | 每个上传文件后台 1 次 | `settings.llm_parse_model` |

当前五个模型都写在 `agent-app/src/agent_app/config.py` 的默认值里（`agent-app/.env`
不再配置模型名）：**五个调用点全部是 `deepseek-flash`**（模型版本
`DeepSeek-V4.1-Flash`），走 DeepSeek 官方接口 `https://api.deepseek.com`。

官方只有 `deepseek-flash` 与 `deepseek-v4-pro` 两个模型。需要更强推理时，优先把 #4
（数据分析）改成 `deepseek-v4-pro`——它是五个里唯一一个「算错了不报错」的调用点；
#2/#3/#5 只改文本与抽取，降级只会变糙，不会变错。

**注意思考模式：**DeepSeek 官方接口默认开启思考（默认档 `high`），关闭必须显式传
`extra_body={"thinking": {"type": "disabled"}}`；官方要带 `tools` 时把每轮的
`reasoning_content` 原样回传，否则 400（实测当前链路能正常回环）。本项目把强度档设为
`low`，配置项是 `llm_thinking_effort`（`llm/client.py` 的 `get_llm()`）。

**注意结构化输出：**DeepSeek 官方接口不支持 `response_format={"type":
"json_schema"}`（回 400 `This response_format type is unavailable now`）。所以本项目
所有结构化输出都走 `llm/client.py` 的 `structured_output()`，它固定用
`method="function_calling"`。这个组合要求**思考关闭**（开着会回 400 `Thinking mode
does not support this tool_choice`）。

**#4（数据分析）不开启思考**：`get_ds_llm()` 走 `get_summary_llm()` 共用的
`_build_utility_llm()`，那个工厂固定 `streaming=False` + `extra_body={"thinking":
{"type": "disabled"}}`。Plan/Code 都是结构化输出，思考只会拉长时延与成本；如果哪次
发现 Plan 反复误判，再单独为它开。

编号是**登记顺序**，不是代码出现顺序——#5 的代码比 #4 早得多，因为 DS 子 Agent 是
最后一个被登记进来的。

## 三、逐项说明

### 1. 对话生成

- **谁在调用**：`agent-app/src/agent_app/llm/agent.py:70` 的 `create_agent(get_llm(), ...)`
  装配出 LangGraph 图；真正发起在 `agent-app/src/agent_app/api/v1/chat.py:674`
  的 `get_agent().astream(...)`。
- **客户端与参数**（`agent-app/src/agent_app/llm/client.py:105-120`）：
  `temperature=0.7`、`streaming=True`、
  `extra_body={"enable_thinking": True}`（仅当 `settings.llm_enable_thinking`）。
- **system prompt**：`agent-app/src/agent_app/llm/client.py:14` 的模块级常量 `SYSTEM_PROMPT`。
  长期记忆不在这里拼，而是由 `agent-app/src/agent_app/memory/middleware.py` 在
  每次模型调用前临时追加（原因见该模块 docstring）。
- **输入规模**：会话全部消息（受摘要压缩控制，触发阈值见 `settings.summary_trigger_tokens`
  / `settings.summary_trigger_fraction`）+ system prompt + 记忆段（上限
  `settings.memory_max_injected` 条）。
- **对模型的核心要求**：
  1. **流式可用**，首 token 延迟低（用户直接感知，是体验的第一指标）。
  2. **中文表达质量**：健康类内容说错话的代价高于普通闲聊。
  3. **长上下文**：一轮问答可能带几万 token 的历史与记忆。
  4. **指令遵循**：system prompt 里的边界（不做诊断、不给药物剂量建议、
     单位换算与异常判定由代码负责）必须被守住。
  5. 支持或至少不破坏 thinking/reasoning 通道（前端「思考块」依赖它）。
- **换模型时的验收标准**：
  1. TTFT（首 token 延迟）对比，取多次中位数。
  2. 准备一组固定健康问答（10~20 条），人工对比：是否越界诊疗、
     是否编造数值、是否遵守「不知道就说不知道」。
  3. 跑一遍长会话（触发一次摘要后再问涉及早期内容的问题），
     看是否还能答对。
  4. 确认 thinking 分片仍能正常流式（前端 `ThinkingBlock` 不应变空）。
  5. 确认流式 usage 仍能拿到（用量统计依赖它）。
- **已知失败模式**：换到不支持 `reasoning_content` 的模型，思考块会永远为空；
  换到上下文窗口更小的模型，摘要触发点需要同步下调 `summary_trigger_tokens`。

### 2. 上下文摘要

- **谁在调用**：`agent-app/src/agent_app/llm/context.py:132`，
  在 `build_summarization_middleware()`（`agent-app/src/agent_app/llm/context.py:118`）里
  作为 `SummarizationMiddleware` 的模型。
- **客户端与参数**（`agent-app/src/agent_app/llm/client.py:122-145`）：
  `temperature=0.2`、`streaming=False`、
  `profile={"max_input_tokens": settings.llm_max_input_tokens}`（**这个 profile 不能省**，
  中间件靠它判断什么时候必须压缩）。
- **提示词**：`SUMMARY_PROMPT`（`agent-app/src/agent_app/llm/context.py:50`），
  框架内置 `DEFAULT_SUMMARY_PROMPT` 的中文译文。
- **token 计数**：`chinese_token_counter`（`agent-app/src/agent_app/llm/context.py:110`），
  本地估算，不调模型。
- **触发频率**：只在消息数/长度超过阈值时触发，不是每轮都跑。
- **对模型的核心要求**：中文长文本压缩能力、**信息保真**（事实、数值、时间、
  用户明确说过的约束不能压缩掉）、便宜、快（这段时间用户要等）。
- **换模型时的验收标准**：
  1. 拿一段真实长会话跑压缩，逐条核对摘要里是否保留了
     用户提到的关键事实与数值、时间。
  2. 压缩后再问一个只出现在被压缩部分的问题，看新模型能否借助摘要答对
     （这是摘要质量最直接的检验）。
  3. 对比耗时与单价。
- **已知失败模式**：压缩掉「用户说过对某药过敏」这类信息，之后所有回答都错，
  而且用户很难察觉——所以这一项的验收重点是**信息保真**，不是文笔。

### 3. 长期记忆抽取

- **谁在调用**：`agent-app/src/agent_app/memory/extract.py:158`；
  由 `agent-app/src/agent_app/api/v1/chat.py` 在回复落库之后用
  `spawn_memory_extraction()` 起后台任务，不阻塞回复。
- **客户端与参数**：`get_memory_llm().with_structured_output(MemoryOps)`，
  非流式、`temperature=0.2`。
- **提示词**：`EXTRACT_PROMPT`（`agent-app/src/agent_app/memory/extract.py` 内），
  与 `MemoryOp` / `MemoryOps`（同文件）的字段是一体的，改动要一起改。
- **输入规模**：本轮用户消息 + 本轮助手回复 + 该用户现有记忆清单
  （上限 `DIGEST_LIMIT = 200` 条，`agent-app/src/agent_app/memory/store.py`）。
- **对模型的核心要求**：
  1. **结构化输出必须可靠**（严格 JSON schema）。纯文本模型直接不可用。
  2. 能执行排除规则：不记助手自己的建议、不记一次性状况、不记别人的事、
     不记条件句。
  3. 能对照现有清单判断 `add` 还是 `update`，并**准确引用清单里的 id**
     （编造的 id 会被 `_parse_id` 丢掉，表现为这次 `update` 不生效）。
  4. 便宜、快（每轮都跑，是固定成本）。
- **换模型时的验收标准**：
  1. 准备一批固定对话样本（含正例与反例），人工标注期望的记忆条目，
     跑完后统计三个数：**误记率**（写了不该写的）、**漏记率**、
     **add/update 选择是否正确**。
  2. 统计 `update` 操作的命中率——这一项直接反映 id 引用准确性。
  3. 观察 `confidence` 字段的分布（模型自报置信度**没有校准**，
     只用于相对排序与事后分析，不能当硬阈值、不能跨模型比绝对值）。
  4. 确认结构化输出失败率（解析失败会被记成 `memory_extract_failed` 日志）。
- **已知失败模式**：结构化输出不稳定 → 抽取长期静默失败（因为没有报错打扰用户，
  只在日志里）；把助手自己的建议记成用户事实，是最主要的脏记忆来源。

### 4. 数据分析（DS 子 Agent）

- **谁在调用**：`agent-app/src/agent_app/ds/graph.py:94` 的 `LlmDsModel`，装配在
  `agent-app/src/agent_app/ds/graph.py:306` 的 `run_analysis()` 里。一个客户端服务
  两个节点：**Plan**（问题 → 分析计划）与 **Code**（计划 → pandas 代码）。
- **客户端与参数**（`agent-app/src/agent_app/llm/client.py:158`）：`temperature=0.2`、
  `streaming=False`；Plan 走 `with_structured_output(AnalysisPlan)`，Code 走
  `with_structured_output(_CodeDraft)`。温度取 0.2 而不是 0.0，是因为 Coder 会重试：
  0.0 下模型容易把同一份代码逐字再交一次，把重试预算白烧掉。
- **提示词**：`agent-app/src/agent_app/ds/prompts.py:44` 的 `PLAN_SYSTEM` 与
  `agent-app/src/agent_app/ds/prompts.py:66` 的 `CODE_SYSTEM`；用户 prompt 由
  `plan_prompt()`（同文件 `:125`）、`code_prompt()`（同文件 `:135`）、
  `fix_prompt()`（同文件 `:152`）拼装。
- **输入规模**：用户问题 + **指标目录摘要**（`agent-app/src/agent_app/ds/dataset.py:219`
  的 `build_dataset()` 产出：每个指标的样本数、时间跨度、单位、区间/文本占比）。
  **原始数据行不进 prompt**——它只被渲染成长表 CSV 交给沙箱，由执行器加载
  （`agent-app/src/agent_app/ds/runner.py:54`）。
- **对模型的核心要求**：
  1. **结构化输出必须可靠**：`AnalysisPlan` 要能直接进下一个节点，不是给人看的散文。
  2. 能把开放式问题（「我最近状态怎么样」）映射到**具体指标 + 具体时间窗**，
     而不是只回答用户字面点名的那几个指标。
  3. 能选对统计方法，并把**适用性假设**写成可执行步骤
     （`agent-app/src/agent_app/ds/schemas.py:64` 的 `StatisticSpec.assumptions`）。
     参照：论文实测把假设写进计划后，数据充足性检查的通过率从 5.3% 提到 66.5%。
  4. 能生成可运行的 pandas 代码：固定签名 `analysis(df)`，返回值必须符合契约。
  5. 数据不够时**主动说不**（`AnalysisPlan.sufficient=False`），而不是硬算一个数。
  6. **不许把数字写进自然语言**：所有数值必须来自沙箱执行结果。
- **换模型时的验收标准**：
  1. 准备固定数据集 + 固定问题集，统计**首次生成的通过率**（不是重试之后的）。
     参照：PHA 论文里重试把成功率从第 1 次的 75.5% 抬到第 5 次的 79.0%，
     所以首次质量才是选型的核心指标。
  2. 统计 `agent-app/src/agent_app/ds/checks.py:121` 的 `check_result()` 拦截率，
     分三类（样本量对不上、同一指标出现多个单位、区间被当标量）。目标是让
     「代码跑通但结果错」降到 0。
  3. 统计 `sufficient=False` 的判定是否合理：该拒的没拒是错答，
     不该拒的拒了是漏答。
  4. 重试次数分布，均值越接近 1 越好。
  5. 抽查生成的代码里有没有 `try/except` 兜底——有就是「静默给出错数值」的隐患。
- **已知失败模式**：把 `try/except` 写进代码，把失败吞成空结果；把区间值或时刻当
  标量算进均值；编造样本量（这三项由 `checks.py` 拦）；**选了一个对当前数据分布
  不适用的检验**——这一项目前没有自动拦截，只体现在输出的 `warnings` 里。

### 5. 文档解析抽取

- **谁在调用**：`agent-app/src/agent_app/parsing/extract.py:25` 的 `extract_report()`，
  由解析 worker（`agent-app/src/agent_app/parsing/worker.py`）从 Redis 队列里取出任务后调用。
- **客户端与参数**（`agent-app/src/agent_app/llm/client.py:142`）：`temperature=0.0`、
  `streaming=False`，走 `with_structured_output(LlmExtraction)`
  （`agent-app/src/agent_app/parsing/schema.py`）。**这是全库唯一温度为 0.0 的调用点**：
  抽取的任务是从原文里搬值，不是演绎；温度升高只会让同一个 `value` 每次被抄成不同写法。
- **提示词**：`agent-app/src/agent_app/parsing/prompt.py:8` 的 `EXTRACT_PROMPT`（system），
  human 消息是整页 OCR 纯文本。
- **输入规模**：一份报告的整页 OCR 文本，**不切分**。所以长报告的输入量随页数线性增长，
  超过 `settings.llm_max_input_tokens` 的报告会在这一层失败。
- **对模型的核心要求**：
  1. **逐行抄，不换算**：原文写 `10小时33分钟` 就交 `10小时33分钟`，换算成分钟是下游
     `agent-app/src/agent_app/ds/normalize.py` 的事。
  2. **拆不出数值的东西也要带上**：`52-171` 这类区间、`肝内钙化灶` 这类发现项，原文怎么
     写就怎么抄，**不要取中点、不要丢弃**。
  3. **日期原文照抄**（`date_raw`），**不要自己补年份**——补年份由
     `agent-app/src/agent_app/parsing/dates.py` 的 `normalize_date()` 用上传时间做候选，
     不经过模型。
  4. 原文没有的项不要补，宁可少交也不要编。
- **换模型时的验收标准**：
  1. 用同一批 OCR 文本对比**抽取条数**与逐字段值——换模型后条数少了几条是最常见的退化。
  2. 统计 `value` 被改写的比例：只要原文能直接找到的值，换了写法（换算、取中值、补单位）
     就是失败。
  3. 统计 `date_raw` 被“修好”的比例：抄成合法日期而不是原文，说明模型在自作主张。
- **已知失败模式**：把 `10小时33分钟` 换算成 `633`（下游会再换算一次，结果错两次）；
  把区间取中点；把参考范围写进 `value`；给没写年份的日期编一个年份。

## 四、明确**没有**用模型的地方

避免以后误以为这些也依赖模型：

| 功能 | 实现 | 位置 |

## 六、换模型的操作步骤

1. 开发期改 `agent-app/src/agent_app/config.py` 里的默认值：`llm_model`（对话）、
   `llm_summary_model`（压缩）、`llm_memory_model`（记忆抽取）、`llm_parse_model`
   （文档解析）、`llm_ds_model`（数据分析）；后四个留空即回落 `llm_model`，
   但 **`llm_ds_model` 建议写死具体模型名**（理由见第三节 #4）。
   `uvicorn --reload` 会自动重启进程（客户端是 `lru_cache` 单例，
   不重启不会换），改完等几秒即可。
   上线或临时切换则写进 `agent-app/.env` 的 `LLM_MODEL` / `LLM_SUMMARY_MODEL` /
   `LLM_MEMORY_MODEL` / `LLM_PARSE_MODEL` / `LLM_DS_MODEL`，并
   `docker compose -f docker/docker-compose.yml up -d backend`
   **重建**容器（`restart` 不会重读 `env_file`）。
2. 按第三节各调用点的「验收标准」跑一遍。
3. 更新本文件第二节总览里的「当前模型」一栏。
