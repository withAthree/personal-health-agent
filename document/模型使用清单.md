# 模型使用清单

> 用途：把「这个项目在哪些地方用了大模型、用的是哪个模型、参数是什么」集中记在一处，
> 以便后续做**模型选型**时有据可依地替换，而不是随手换一个便宜的试试。
>
> 每新增一个模型调用点都要在本文件登记；每个调用点的「验收标准」一栏是这份文档的核心，
> 它决定换模型之后要拿什么标准去判断新旧模型谁更好。
>
> 代码位置按当前版本记录，改动代码后请同步更新本文件。

## 一、怎么读这份清单

- **开发期改 `agent-app/src/agent_app/config.py` 的默认值就行**：后端跑
  `uvicorn --reload`，改完进程自动重启、`lru_cache` 的客户端跟着重建，不用碰容器。
- **上线或临时切换才走 `.env`**（`agent-app/.env`，由 `docker/docker-compose.yml`
  的 `env_file` 注入）：`Settings` 用 `SettingsConfigDict(env_file=BASE_DIR / ".env")`
  读取，优先级是「环境变量 > 代码默认值」，所以 `.env` 里配了就覆盖代码默认值。
  这种情况**必须重建容器**：`docker compose restart backend` 不会重读 `env_file`，
  要用 `docker compose -f docker/docker-compose.yml up -d backend`。
- 变量命名与 `config.py` 字段的对应关系是「字段名大写」：`llm_model` ← `LLM_MODEL`，
  `llm_summary_model` ← `LLM_SUMMARY_MODEL`，`llm_memory_model` ← `LLM_MEMORY_MODEL`。
- 客户端都是进程级单例：**换模型必须重启进程**（重启容器即可），热改环境变量不会让
  已有进程换模型。
- 所有客户端工厂都在 `agent-app/src/agent_app/llm/client.py`：

  | 工厂 | 定义位置 | 缓存口径 | 用途 |
  |------|---------|---------|------|
  | `get_dialog_llm(model)` | `agent-app/src/agent_app/llm/client.py:105` | **按模型名** | 对话生成（要流式、要思考块）；参数化是为了多 Agent 解耦 |
  | `get_llm()` | `agent-app/src/agent_app/llm/client.py:133` | `maxsize=1` | 单 Agent 时代的对话客户端，等价于 `get_dialog_llm(settings.llm_model)`，两者**共用缓存** |
  | `get_summary_llm()` | `agent-app/src/agent_app/llm/client.py:144` | `maxsize=1` | 上下文摘要（压缩），非流式 |
  | `get_memory_llm()` | `agent-app/src/agent_app/llm/client.py:154` | `maxsize=1` | 长期记忆抽取，非流式 + 结构化输出 |
  | `get_parse_llm()` | `agent-app/src/agent_app/llm/client.py:164` | `maxsize=1` | 文档解析抽取，非流式、温度 0.0 |
  | `get_utility_llm(model, *, temperature=0.2)` | `agent-app/src/agent_app/llm/client.py:201` | **按模型名 + 温度** | 旁路客户端（非流式、低温）；多 Agent 的控制节点用它 |

  `get_dialog_llm()` 返回 `ChatOpenAIWithReasoning`（`agent-app/src/agent_app/llm/client.py:52`），
  它修正了 provider 两处非标准行为：把 `reasoning_content` 从 `additional_kwargs`
  里捡回来、补上流式 usage。
  旁路客户端共用私有构造 `_build_utility_llm()`（`agent-app/src/agent_app/llm/client.py:179`），
  但**模型名各自独立**：摘要、记忆抽取、文档解析分别由 `settings.llm_summary_model`、
  `settings.llm_memory_model`、`settings.llm_parse_model` 决定，**留空（默认）表示回落到
  `settings.llm_model`**。
- **多 Agent 的角色 → 模型名映射只在 `agent-app/src/agent_app/orchestration/llm.py`**
  （`get_agent_llm()` 在 `:41`。`get_general_llm()` 在 `:53`、`get_orchestrator_llm()` 在 `:67`）：节点代码只写角色名
  （`get_agent_llm("ds")`），不认识模型名。所以「给某个 Agent 单独换模型」= 只改
  `config.py`（或 `.env`），**不动任何业务代码**。

## 三、逐项说明

### 1. 对话生成

- **谁在调用**：`agent-app/src/agent_app/llm/agent.py:70` 的 `create_agent(get_llm(), ...)`
  装配出 LangGraph 图；真正发起在 `agent-app/src/agent_app/api/v1/chat.py:674`
  的 `get_agent().astream(...)`。
- **客户端与参数**（`agent-app/src/agent_app/llm/client.py:105-120`）：
  `temperature=0.7`、`streaming=True`、
  `extra_body={"enable_thinking": True}`（仅当 `settings.llm_enable_thinking`）。
- **system prompt**：`agent-app/src/agent_app/llm/client.py:14` 的模块级常量 `SYSTEM_PROMPT`。
  长期记忆不在这里拼，而是由 `agent-app/src/agent_app/memory/middleware.py` 在
  每次模型调用前临时追加（原因见该模块 docstring）。
- **输入规模**：会话全部消息（受摘要压缩控制，触发阈值见 `settings.summary_trigger_tokens`
  / `settings.summary_trigger_fraction`）+ system prompt + 记忆段（上限
  `settings.memory_max_injected` 条）。
- **对模型的核心要求**：
  1. **流式可用**，首 token 延迟低（用户直接感知，是体验的第一指标）。
  2. **中文表达质量**：健康类内容说错话的代价高于普通闲聊。
  3. **长上下文**：一轮问答可能带几万 token 的历史与记忆。
  4. **指令遵循**：system prompt 里的边界（不做诊断、不给药物剂量建议、
     单位换算与异常判定由代码负责）必须被守住。
  5. 支持或至少不破坏 thinking/reasoning 通道（前端「思考块」依赖它）。
- **换模型时的验收标准**：
  1. TTFT（首 token 延迟）对比，取多次中位数。
  2. 准备一组固定健康问答（10~20 条），人工对比：是否越界诊疗、
     是否编造数值、是否遵守「不知道就说不知道」。
  3. 跑一遍长会话（触发一次摘要后再问涉及早期内容的问题），
     看是否还能答对。
  4. 确认 thinking 分片仍能正常流式（前端 `ThinkingBlock` 不应变空）。
  5. 确认流式 usage 仍能拿到（用量统计依赖它）。
- **已知失败模式**：换到不支持 `reasoning_content` 的模型，思考块会永远为空；
  换到上下文窗口更小的模型，摘要触发点需要同步下调 `summary_trigger_tokens`。

### 2. 上下文摘要

- **谁在调用**：`agent-app/src/agent_app/llm/context.py:132`，
  在 `build_summarization_middleware()`（`agent-app/src/agent_app/llm/context.py:118`）里
  作为 `SummarizationMiddleware` 的模型。
- **客户端与参数**（`agent-app/src/agent_app/llm/client.py:122-145`）：
  `temperature=0.2`、`streaming=False`、
  `profile={"max_input_tokens": settings.llm_max_input_tokens}`（**这个 profile 不能省**，
  中间件靠它判断什么时候必须压缩）。
- **提示词**：`SUMMARY_PROMPT`（`agent-app/src/agent_app/llm/context.py:50`），
  框架内置 `DEFAULT_SUMMARY_PROMPT` 的中文译文。
- **token 计数**：`chinese_token_counter`（`agent-app/src/agent_app/llm/context.py:110`），
  本地估算，不调模型。
- **触发频率**：只在消息数/长度超过阈值时触发，不是每轮都跑。
- **对模型的核心要求**：中文长文本压缩能力、**信息保真**（事实、数值、时间、
  用户明确说过的约束不能压缩掉）、便宜、快（这段时间用户要等）。
- **换模型时的验收标准**：
  1. 拿一段真实长会话跑压缩，逐条核对摘要里是否保留了
     用户提到的关键事实与数值、时间。
  2. 压缩后再问一个只出现在被压缩部分的问题，看新模型能否借助摘要答对
     （这是摘要质量最直接的检验）。
  3. 对比耗时与单价。
- **已知失败模式**：压缩掉「用户说过对某药过敏」这类信息，之后所有回答都错，
  而且用户很难察觉——所以这一项的验收重点是**信息保真**，不是文笔。

### 3. 长期记忆抽取

- **谁在调用**：`agent-app/src/agent_app/memory/extract.py:158`；
  由 `agent-app/src/agent_app/api/v1/chat.py` 在回复落库之后用
  `spawn_memory_extraction()` 起后台任务，不阻塞回复。
- **客户端与参数**：`get_memory_llm().with_structured_output(MemoryOps)`，
  非流式、`temperature=0.2`。
- **提示词**：`EXTRACT_PROMPT`（`agent-app/src/agent_app/memory/extract.py` 内），
  与 `MemoryOp` / `MemoryOps`（同文件）的字段是一体的，改动要一起改。
- **输入规模**：本轮用户消息 + 本轮助手回复 + 该用户现有记忆清单
  （上限 `DIGEST_LIMIT = 200` 条，`agent-app/src/agent_app/memory/store.py`）。
- **对模型的核心要求**：
  1. **结构化输出必须可靠**（严格 JSON schema）。纯文本模型直接不可用。
  2. 能执行排除规则：不记助手自己的建议、不记一次性状况、不记别人的事、
     不记条件句。
  3. 能对照现有清单判断 `add` 还是 `update`，并**准确引用清单里的 id**
     （编造的 id 会被 `_parse_id` 丢掉，表现为这次 `update` 不生效）。
  4. 便宜、快（每轮都跑，是固定成本）。
- **换模型时的验收标准**：
  1. 准备一批固定对话样本（含正例与反例），人工标注期望的记忆条目，
     跑完后统计三个数：**误记率**（写了不该写的）、**漏记率**、
     **add/update 选择是否正确**。
  2. 统计 `update` 操作的命中率——这一项直接反映 id 引用准确性。
  3. 观察 `confidence` 字段的分布（模型自报置信度**没有校准**，
     只用于相对排序与事后分析，不能当硬阈值、不能跨模型比绝对值）。
  4. 确认结构化输出失败率（解析失败会被记成 `memory_extract_failed` 日志）。
- **已知失败模式**：结构化输出不稳定 → 抽取长期静默失败（因为没有报错打扰用户，
  只在日志里）；把助手自己的建议记成用户事实，是最主要的脏记忆来源。

### 4. 多 Agent 编排（`agent-app/src/agent_app/orchestration/`）

**状态：编排器（单位 2）、「不需要分配任务」的通用对话（流程调整）与数据科学 Agent
（单位 4）已各接上一个调用点，`domain_expert()` / `health_coach()` / `integrate()` /
`reflect()` / `memory()` 仍是空节点**：`agent-app/src/agent_app/orchestration/nodes.py` 的
`orchestrator()` 调 `_decide()` → `get_orchestrator_llm().with_structured_output(RoutingDecision)`；
`finalize()` 在没有 `draft` 时调 `_answer_directly()` → `get_general_llm().astream(...)`；
`data_science()` 调 `_run_agent()` → `get_agent_llm("ds")` 加一轮工具循环。

- **配置项**（`agent-app/src/agent_app/config.py:58-76`）：`llm_ds_model`、`llm_de_model`、
  `llm_hc_model`（三个业务 Agent 的对话模型）、`llm_orchestrator_model`（控制节点）。
  **四个都默认为空串 = 回落 `llm_model`**，所以默认行为与单 Agent 完全一致。
- **工厂**：`agent-app/src/agent_app/orchestration/llm.py` 的 `get_agent_llm()`（`:41`，流式对话）、
  `get_general_llm()`（`:53`，流式对话，固定用 `settings.llm_model`）与 `get_orchestrator_llm()`
  （`:67`，非流式、**温度 0.0**）。
- **通用对话为什么不用 `get_orchestrator_llm()`**：它是用户**看得见的正文**，必须流式；
  它也不属于三个业务 Agent（没有分工），所以直接拿对话主模型，与单 Agent 时期同一条路径。
  它没有单独的配置项：`llm_model` 就是它的模型名。
- **为什么控制节点不用 `get_llm()`**：它是为「与用户直接对话」调的（temperature 0.7、流式）；
  编排/整合/反思/收尾只要求稳定吐出符合 schema 的结构化输出，所以走
  `get_utility_llm()`（非流式、低温、带 `profile`）。
- **业务 Agent 为什么走工具循环（`_run_agent()`）而不是「我们先查好数据再塞进提示词」**：
  取哪些指标、取多长区间、要不要连报告结论一起看，是**判断**，按「最大化模型能力」这条
  原则交给模型；我们的活是把工具写好（`agent-app/src/agent_app/tools/health.py`，身份只从
  闭包进来、不暴露 `user_id` 参数）并把循环夹住（`_MAX_TOOL_ROUNDS = 6`）。同一轮里模型
  要多轮取数就是这个循环在跑，所以一次 DS 产出的模型调用次数不固定（1~7 次）。
- **编排为什么用 0.0 而不是旁路默认的 0.2**：编排是**分类**任务（选角色、派查询），
  不是创作。0.2 下极短输入（「你好」「收到」）会在 `general` 与 `ds` 之间来回摇摆（实测
  同一句「你好」8 次里 6 次落 `ds`）；改成 0.0 后复测 40/40 稳定落 `general`。温度归零
  消掉的是采样噪声，provider 侧仍不保证逐次比特级一致，所以换模型/换 provider 后要重测。
- **换模型时的验收标准**：
  1. **业务 Agent（含已接上的数据科学 Agent）**：准备一批各自领域的固定问题
     （DS 用「分析我的血糖趋势」这类
     需要取数的问题，DE 用需要依据的问题，HC 用「坚持不下来怎么办」这类行为改变问题），
     换模型后人工对比：是否越界诊疗、是否编造数值、是否遵守「不知道就说不知道」、
     语气是否符合该角色设定。**DS 另有一条**：换模型后确认它仍会先调
     `list_health_metrics` 拿到指标名、再取序列，而不是凭常识报数字。
  2. **三个业务 Agent 还共用一条硬指标**：过程块（thinking / tool_call / tool_result）
     必须仍能流式产出——前端多 Agent 时间线依赖它。
  3. **控制节点**：换模型后统计**结构化输出的解析失败率**（失败会降级成通用对话，
     属静默失败）；再拿一批固定问题人工核对路由准确性（主/辅 Agent 选错会污染整条
     链路，是这套编排里最贵的一类错误）。
     编排器的**换模型验收基线**（2026-10-14「#1 `deepseek-ai/DeepSeek-V3.2`」实测，
     18 条固定输入，附记忆与文件清单）：
     带明确诉求的 13 条全部正确——血糖趋势/体重对比 → `ds`；指标解释、用药、
     指南、体检结论 → `de`；坚持不下来、减肥目标 → `hc`；预约医生、与健康无关 → 
     `general`。多意图的两条正确派了支持角色（「血糖趋势 + 二甲双胍影响」→`de`+`ds`；
     「睡眠不好会不会影响血糖 + 上个月血糖数据」→`de`+`ds`）。
     **极短寒暄的稳定性（2026-10-14 复测）**：把温度从 0.2 降到 0.0 之前，「你好」「收到」
     在不同轮次分别落到 `general` 与 `ds`；改到 0.0 后复测 `你好`/`收到`/`好的`/`嗯`/`谢谢`
     各 8 次，**40/40 全部落 `general`**（prompt 里已把这几个词按闭集列举）。换模型后重跑
     这 18 条 + 这批短寒暄，比对是否仍稳定。
  4. 换任何一个角色的模型都要确认**其他角色没有跟着变**——这正是「解耦」的验收点。
- **已知失败模式**：把某个角色的模型名写错（如漏了前缀）→ provider 直接报 404，
  表现为该节点整条路径失败；`lru_cache` 是进程级缓存，改 `config.py` 后不重启进程不会生效。

## 六、换模型的操作步骤

1. 开发期改 `agent-app/src/agent_app/config.py` 里的默认值：`llm_model`（对话）、
   `llm_summary_model`（压缩）、`llm_memory_model`（记忆抽取）、`llm_parse_model`（文档解析）；
   后三个留空即回落 `llm_model`。多 Agent 再加 `llm_ds_model` / `llm_de_model` /
   `llm_hc_model`（三个业务 Agent）与 `llm_orchestrator_model`（控制节点），同样留空回落。
   `uvicorn --reload` 会自动重启进程（客户端是进程级缓存，
   不重启不会换），改完等几秒即可。
   上线或临时切换则写进 `agent-app/.env` 的 `LLM_MODEL` / `LLM_SUMMARY_MODEL` /
   `LLM_MEMORY_MODEL` / `LLM_PARSE_MODEL` / `LLM_DS_MODEL` / `LLM_DE_MODEL` /
   `LLM_HC_MODEL` / `LLM_ORCHESTRATOR_MODEL`，并 `docker compose -f docker/docker-compose.yml up -d backend`
   **重建**容器（`restart` 不会重读 `env_file`）。
2. 按第三节各调用点的「验收标准」跑一遍。
3. 更新本文件第二节总览里的「当前模型」一栏。
